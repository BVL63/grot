# ГРОТ 2.0 — переход на единый механизм годов

Статус: рабочий план разработки. Стартовая точка: ГРОТ 0.3.205, commit `6f1d69d85528b6e7c4e4ebd9f03c8ed822b2e31c`.

## Основные правила

1. Одна и та же форма, таблица, справочники и набор действий для **любого года**; год — параметр, а не ветка интерфейса.
2. Данные **каждого** года независимы: периоды отпусков, состав графиков, назначения групп, минимальная численность, конфликты, исключения, решения об утверждении и календарь.
3. Общие справочники сотрудников и структуры организации; состав каждого графика и данные на конкретный год фиксируются отдельно. При создании нового года копируются только действующие сотрудники, структура и настройки групп, **без дат отпусков**.
4. Одновременно могут существовать действующий и следующий плановые годы. Изменения в предыдущем году не переписывают даты следующего. КОН/КСН и предварительные остатки помечаются «требуют обновления», если их источник изменился. План не следует автоматически объявлять фактом.
5. График следующего года можно создать в любое время предыдущего года. Срок утверждения — не позднее 17 декабря предыдущего года. Создание следующего года не архивирует действующий.
6. Утверждение — отдельное действие уполномоченного руководителя с проверкой неразрешённых конфликтов и фиксацией решения; администратор может предлагать исключения, но не утверждать.
7. Настоящие архивы прошлых лет используют **тот же интерфейс**; ограничения изменения основаны на роли/статусе, а не на отдельной урезанной форме.
8. При обновлении нельзя уничтожать или изменять данные, сохранённые в `vacations2027`, `vacationStaff2027`, `grot-seasonality-history-v1`, `grotVacationCharts`, `grotAnnualPlansV1`. Особое внимание — исторические записи с фамилиями без однозначного соответствия сотруднику.
9. Резервная копия охватывает все годы. До любой миграции — проверенная резервная копия, возможность отмены и тест сохранения/восстановления. Изменения не должны перезаписывать соседний год.

## Последовательность

- Этап 1: новый модуль хранения данных с API `readYear(year)`, `writeYear(year, patch)` и без удаления старых ключей. Разработать тесты на независимость лет и миграцию.
- Этап 2: перевести отображение календаря и редактор отпусков на выбранный год, сохранив вид и функции 2027 года.
- Этап 3: унифицировать графики, состав, группы, приоритет, контроль пересечений, печать и отчёты.
- Этап 4: подключить производственный календарь по каждому году; добавить статусы утверждения, разрешения исключений, журнал изменений и контроль срока.
- Этап 5: обновить резервирование/восстановление, импорт истории и Windows-сборку; проверить на копиях реальных данных 2025–2028 годов.
- Этап 6: только после успешных тестов выпускать 2.0 как отдельный релиз.

## Сохранённая версия 0.3.205

- Не менять ветку `release/0.3.205`.
- Разработку вести в `develop/2.0`; `main` пока не переносить на 2.0.
- Windows артефакты: [сборка GitHub Actions](https://github.com/BVL63/grot/actions/runs/43405209805): Setup и Portable. Загруженные артефакты имеют ограниченный срок хранения.
- Пользовательские данные в localStorage **не являются частью** исходного кода и сборки: перед тестированием 2.0 сделать резервную копию через интерфейс ГРОТ.
